## Context

ADR-0018 settles that tests authenticate the way a real client does, and that "test accounts are created with the admin flow or the seed, never by weakening lockout or rate-limit settings". It does not say who may create which accounts, nor where that code lives.

The AUT automation plan (`.context/QA/automation/aut/automation-plan.md`) needs principals the framework does not hold:

- Negative and role cases (inactive or deleted user, wrong login mode, lockout, route matrix by role) must not send wrong passwords to the real Administrator account.
- The only credentials the suite knows are the Administrator pair, read by name from the environment. A TenantAdmin password is generated by the server and delivered only by email.
- An Administrator can create a tenant, a UserApp and a non-root platform Admin with a chosen password through the encrypted API.

`agentic-qa-core/references/browser-sessions.md` section 4 forbids an agentic browser session from using an admin or user-management API to create the account it runs as. It states it neither grants nor refuses the same for the KATA suite, and leaves that to a per-project test-architecture decision recorded as an ADR. This is that record.

## Decision

The suite may create its own test principals through the Administrator API, as test data, under these conditions.

1. **What may be created:** tenants, UserApps and non-root platform Admins, each with unique generated names and a generated password that satisfies the product's complexity rules. A generated tenant sets its failed-login limit explicitly.
2. **Through the encrypted session only:** creation runs over the ADR-0018 fixture (`SecureApi` and the crypto helper): handshake, envelope, cookie and CSRF. No plaintext call and no non-production fallback.
3. **Where the code lives:**
   - `TenantsApi`, `UsersApi` and `UserAppsApi` extend `SecureApi` and only create, change or delete test data. They carry no ATC, except the one that is itself the case under test (unlocking a locked UserApp).
   - `AccessApi` holds the ATCs for access and token-integrity cases.
   - `GeneratedPrincipalsSteps` (Steps layer, undecorated, instantiated directly) owns its own request context and handshake, creates the principals and deletes them in a `finally`.
4. **Signing in stays real:** a generated principal enters through the real login (the SPA form or the encrypted login endpoint). The suite never injects a token or a cookie it did not receive from that login.
5. **The real Administrator account is never locked, modified or used for a negative attempt.** Negative attempts use generated principals.
6. **Foundation gate:** before any case depends on generated data, a throwaway smoke proves that creating, logging in and deleting a generated tenant, UserApp and platform Admin works. If tenant creation with fabricated database coordinates is refused, work on the cases that need it stops and returns to the owner.
7. **Scope:** this covers the KATA suite only. It does not lift the restriction of `browser-sessions.md` section 4 for agentic browser sessions.

## Consequences

- **Positive:** negative, lockout and role cases run without risk to the real account; each run owns its data; no dependency on a mailbox for these principals.
- **Negative / trade-offs:** deletion in this product is soft, so generated tenants and users accumulate (names are unique per run to avoid collisions); the suite now depends on the Administrator API contract for setup, so a change there breaks setup before it breaks a case; the shared address limiter still applies to any failed logins.
- **Neutral / follow-ups:** TenantAdmin cases still need a provisioned account with declared credentials (a separate configuration change); cases that depend on an emailed token still need a readable mailbox or stay manual.

## Alternatives considered

- **Use only the real Administrator for every case.** Rejected: negative and lockout cases would lock the account the whole suite depends on.
- **Create accounts by writing to the database.** Rejected: no test component can do it, and it skips the product's own creation rules.
- **Wait for a provisioned account per role.** Rejected as the only path: it blocks the cases that a generated Admin or UserApp covers fully. It remains the way to cover TenantAdmin.
